# DFEcrab v4.0 集成测试计划

> **文档版本**: 1.0  
> **创建日期**: 2026-04-03  
> **测试周期**: 2026-04-03 ~ 2026-04-10  
> **测试负责人**: DFEcrab QA Team  

---

## 1. 概述

### 1.1 测试目标

本测试计划定义 DFEcrab v4.0 集成测试的范围、策略、环境和通过标准。v4.0 引入了 7 个核心新模块，需要进行全面的集成测试以确保模块间协同工作正常。

### 1.2 测试范围

本次集成测试覆盖以下 7 个核心模块：

| 模块编号 | 模块名称 | 路径 | 测试优先级 |
|---------|---------|------|-----------|
| M1 | 权限系统 | `src/core/security/permissions.py` | P0 |
| M2 | 斜杠命令系统 | `src/core/commands/slash_commands.py` | P0 |
| M3 | 统一工具系统 | `src/core/tools/unified_tools.py` | P0 |
| M4 | 会话持久化 | `src/core/session/persistence.py` | P1 |
| M5 | 上下文引擎 | `src/core/context/engine.py` | P1 |
| M6 | 工作区配置 | `src/core/workspace/config.py` | P1 |
| M7 | Agent 循环增强 | `src/core/agent/enhanced_loop.py` | P1 |

### 1.3 不在测试范围内

- 单元测试（由开发人员在开发阶段完成）
- 性能压力测试（单独的性能测试计划覆盖）
- 安全渗透测试（由安全团队独立执行）
- TUI 界面测试（由前端测试计划覆盖）

---

## 2. 测试策略

### 2.1 测试方法

采用分层测试策略：

```
┌─────────────────────────────────────────┐
│           集成测试金字塔                  │
├─────────────────────────────────────────┤
│  E2E 测试 (20%)                          │
│  ├── 完整工作流测试                       │
│  └── 跨模块交互测试                      │
├─────────────────────────────────────────┤
│  模块集成测试 (50%)                       │
│  ├── 模块间接口测试                       │
│  ├── 数据流测试                          │
│  └── 状态转换测试                        │
├─────────────────────────────────────────┤
│  组件测试 (30%)                          │
│  ├── 单模块功能验证                       │
│  ├── 边界条件测试                        │
│  └── 异常处理测试                        │
└─────────────────────────────────────────┘
```

### 2.2 测试类型

| 测试类型 | 说明 | 自动化程度 |
|---------|------|-----------|
| 功能测试 | 验证模块功能是否符合设计规格 | 100% 自动化 |
| 接口测试 | 验证模块间接口契约 | 100% 自动化 |
| 数据流测试 | 验证数据在模块间正确传递 | 90% 自动化 |
| 异常测试 | 验证错误处理和恢复机制 | 80% 自动化 |
| 回归测试 | 确保新功能不影响现有功能 | 100% 自动化 |

### 2.3 测试执行策略

1. **冒烟测试**: 每次构建后自动执行，验证基本功能
2. **完整集成测试**: 每日定时执行，覆盖所有 21 项测试用例
3. **回归测试**: 代码合并前执行，确保无回归

## 4. 测试通过标准

### 4.1 模块通过标准

每个模块必须满足以下条件方可视为通过：

1. **功能完整性**: 所有设计功能均已实现并验证
2. **测试覆盖率**: 单元测试覆盖率 >= 80%
3. **集成测试**: 所有关联集成测试用例通过
4. **无阻塞缺陷**: 无 P0/P1 级别未解决缺陷
5. **性能指标**: 响应时间符合设计要求

### 4.2 整体通过标准

| 指标 | 要求 |
|-----|------|
| 测试用例通过率 | 100% (21/21) |
| P0 缺陷 | 0 |
| P1 缺陷 | 0 |
| P2 缺陷 | <= 3 (有修复计划) |
| 代码覆盖率 | >= 75% |
| 文档完整性 | 100% |

### 4.3 准入条件

- 所有模块代码已合并至主分支
- 单元测试全部通过
- 代码审查已完成
- 静态分析无严重问题

### 4.4 准出条件

- 所有测试用例执行完毕
- 测试报告已生成并评审
- 已知缺陷已记录并分配
- 发布检查清单已完成

## 7. 风险管理

### 7.1 风险识别

| 风险 | 概率 | 影响 | 缓解措施 |
|-----|------|------|---------|
| LLM 服务不可用 | 中 | 高 | 使用 Mock 服务 |
| 测试环境不稳定 | 低 | 中 | 准备备用环境 |
| 缺陷修复延迟 | 中 | 高 | 提前预留缓冲时间 |
| 测试数据不足 | 低 | 中 | 提前准备测试数据 |

### 7.2 应急计划

- 若测试进度落后超过 20%，启动加班计划
- 若关键缺陷无法及时修复，考虑延迟发布
- 若测试环境问题严重，切换至备用环境
