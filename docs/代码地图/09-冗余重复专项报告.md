## 3. [未启用] · plugins/ 顶层目录（设计了但还没接）

### 状态判定

plugins/ **不是废弃代码**，也不是历史遗留。它是 plugin_framework 插件体系的**物理放置目录**，目录结构完整、execute.py 代码可用，但**当前 PluginLoader 没有扫它**。

### 代码证据

`src/plugin_framework/loader.py`（当前版本）：

```python
class PluginLoader:
    def load_all(self):
        # 硬编码只加载一个插件
        plugin = DFEcrabAgentPlugin()
        self._registry.register(plugin)
        return [plugin]
```

全局搜索结果：
- 没有任何代码 `os.listdir("plugins/")` 或 `glob("plugins/*")` 来扫描这个目录
- `PluginLoader.load_all()` 的 `plugin_dir` 参数**接受但从未使用**（设计了但没接入）
- Gateway 的 HTTP 路由 `/api/plugins/{plugin_name}` 操作的是 `src/plugin_framework/PluginRegistry`，不是顶层 plugins/

### 为什么和 skills/ 有字节级重复？

33 个 plugins 目录里，≥ 15 个 execute.py 与 skills/ 下同名技能**字节完全一致**（calculate、echo、planner、web-fetch、dm_query…）。这是因为：

> plugins/ 目录设计时，是想让 plugin_framework 的 PluginLoader 扫描加载的。
> 但后来实际走了 SkillLoader 扫描 skills/ 的路线，就没回头把 plugins/ 里的重复代码清掉。
> **不是故意留的僵尸，是迁移时忘了清理。**

### plugins/ 当前价值

| 维度 | 评估 |
|---|---|
| 代码质量 | 可用（与 skills/ 同字节，运行时没问题） |
| 加载通路 | **当前无**（PluginLoader 硬编码跳过了） |
| 是否在 roadmap 上 | 待确认——plugin_framework/BasePlugin 体系是否还要继续用？ |
| 和 skills/ 的关系 | 功能重复，但 plugin 走 BasePlugin 接口、skill 走 SKILL.md + execute.py，两套抽象层 |

### 建议（非命令）

1. 如果决定只用 skills/ 体系：可以逐步把 plugins/ 合并或清理
2. 如果 plugin_framework 还要继续用：需要在 `PluginLoader.load_all()` 里加 `glob("plugins/*")` 扫描逻辑，把 plugins/ 里的目录真正接进去
3. **在做决定之前不要删**——它不是废代码，只是还没接

## 4. [开发中] · 半成品模块

### 4.1 task_engine/（孤立模块，8 py）

**状态**：全仓库搜索 `import task_engine` 仅命中其自身内部 2 处（`example.py` → `cli_integration.py`），**无任何 src/、scripts/、dfecrab CLI 引用它**。

目录内容：
- `TaskPlanner` / `TaskExecutor` / `TaskDisplay` 三个核心类
- `cli_integration.py`（想接入 CLI 但没人调它）
- `example.py`（示例脚本）

**判定**：这是一个**早期任务引擎原型**，后来真实的任务系统在 `src/task/` 里实现了，原型就留在了 task_engine/。和 plugins/ 不同——task_engine/ 不是"没接上"，是**功能已被 src/task/ 完全取代**。标记为 `[开发中]` + `[待确认]`。

### 4.2 self-improving-agent（2 处，plugins + skills 各一份）

**状态**：`[开发中]` + `[已损坏]`。import 了三个当前 src/ 不存在的符号：

| 代码写的 | 实际在哪 |
|---|---|
| `from src.agent import SelfImprovingAgent` | ❌ src/agent/__init__.py 不导出，整个类不存在 |
| `from src.hooks import HookManager` | ❌ src/hooks/ 模块不存在。`HookManager` 在 `src/monitoring/hooks.py` |
| `from src.memory import LearningMemory` | ❌ 不存在 |

**判定**：这个技能/插件是**按旧版 src/ 结构写的**，src/ 重构后路径变了、类也没迁过来，没跟着更新。如果想恢复，有两种路：
1. 修正 import 路径（`src.monitoring.hooks`、在 `src/memory/__init__.py` 里补上 LearningMemory 导出、SelfImprovingAgent 重新实现）
2. 如果不需要自反思 Agent 功能了，这两份直接删掉就行

### 4.3 src/memory/ 三套管理器并存

**状态**：`[开发中]`（重构未完成）。

`src/memory/__init__.py` 同时导出：
- `UnifiedMemoryManager` —— 主实现，773 行真代码
- `MemoryManager` —— **legacy 兼容层**，只有 4 行空类（从旧路径 re-export）
- `LongTermMemoryManager` —— 独立实现，410 行

还有命名不一致：`__init__.py` 用 `unified_manager`，子包 `modules/__init__.py` 用 `unified_memory_manager`（多了个 memory_）。

**判定**：memory 层正在做统一化重构，legacy 和 LongTerm 还没清掉。**不能直接删**——需要先全局搜索谁在用 `MemoryManager`（legacy），确认没人用了才能删。

## 6. [项目环境] · 部署必需的运行依赖

> **不是源码，但部署时必须带上。** 和 `logs/`、`data/`（运行时产物）严格区分。

### 6.1 venv/ —— Python 虚拟环境

| 项 | 内容 |
|---|---|
| 作用 | Python 3.12 虚拟环境，打包了项目所有依赖 |
| 内容 | `bin/python3.12`（+x 权限必须）+ `site-packages/`（所有 pip 包） |
| 部署时 | 解压后**必须补执行权限**（Windows zip 丢权限） |
| ⚠️ 丢权限后果 | `bash: ./dfecrab：/home/e8900/DFEcrab/venv/bin/python3：解释器错误: Permission denied` |

### 6.2 wheels/ —— pip 离线安装包

| 项 | 内容 |
|---|---|
| 作用 | 约 15 个 .whl，`pip freeze` 打包 |
| 部署场景 | 目标机器无外网时 `pip install --no-index --find-links=wheels/ -r requirements.txt` |
| 和 venv/ 的关系 | **venv/ 已经包含了这些包**，wheels/ 是备份/新机器初始化用的 |

### 6.3 runtime/ —— Alpine musl 版 Node.js

| 项 | 内容 |
|---|---|
| 作用 | blackxml_topology MCP 的 Node.js 运行时依赖 |
| 内容 | `bin/node.real`（Node.js v24.16.0，Alpine musl 编译）+ `lib/ld-musl-x86_64.so.1`（动态链接器）+ `libc.musl-x86_64.so.1` |
| 部署时 | **ld-musl-x86_64.so.1 必须有 +x 权限** |
| ⚠️ 丢权限后果 | `PermissionError: [Errno 13] Permission denied: '...ld-musl-x86_64.so.1'` |
| 和系统 Node.js 的关系 | Alpine musl 和 glibc 二进制不兼容，不能混着用。如果服务器有 glibc Node.js，可改 blackxml_topology.py 用系统 node |

### 三者对比

| 目录 | 打包进 zip | 部署必带 | 丢权限会炸 | 体积 |
|---|---|---|---|---|
| venv/ | ✅ | ✅ | ✅（python3 无 +x） | ~200MB |
| wheels/ | ✅ | 可选（venv/ 已经有包） | ❌ | ~50MB |
| runtime/ | ✅ | ✅（blackxml_topology 用） | ✅（ld-musl 无 +x） | ~130MB |

## 8. 审计方法说明

本报告基于：

1. **Grep 全局搜索**：`import.*<模块名>` / `from <模块名>` 确认引用关系
2. **Glob 文件扫描**：确认目录存在性、文件数量
3. **LS 目录结构分析**：确认哪些目录是空的、哪些只有壳
4. **源码阅读**：关键文件实际读完后下结论

所有结论都基于实际代码证据，**无推测**。
