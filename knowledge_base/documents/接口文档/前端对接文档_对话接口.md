# 前端对接文档：对话接口（chat）

> 适用版本：DFEcrab 网关（HTTP REST + WebSocket）
> 阅读对象：前端 / 客户端开发人员
> 功能：发起 AI 对话（非流式 / 流式），接收流式事件、最终回复、工具调用链路。
> 本文聚焦**对话（chat）**部分，会话管理见《前端对接文档_会话历史.md》。

---

## 1. 接口总览

对话共 2 个 HTTP 接口 + 2 个 WebSocket 消息类型，**HTTP 与 WebSocket 的流式事件结构完全一致**，前端可复用同一套解析逻辑。

| 通道 | 类型 | 访问地址 / 消息 type | 特点 |
| --- | --- | --- | --- |
| HTTP 非流式 | `POST` | `/api/v2/chat` | 阻塞等待，一次性返回完整结果 |
| HTTP SSE 流式 | `POST` | `/api/v2/chat/stream` | 基于 SSE（`text/event-stream`）逐事件推送 |
| WebSocket 非流式 | 消息 type | `chat` | 一次性返回（走 `message_ack`） |
| WebSocket 流式 | 消息 type | `chat_stream` | 逐事件推送 + `message_ack` 闭环 |

> WebSocket 是**流式对话的推荐通道**（支持取消、可复用 SSE 事件解析），完整协议见本文**第 2 节**；HTTP 两个对话接口见 **5、6 节**。

---

## 2. WebSocket 对接方案（推荐）

### 2.1 连接信息

- 地址：`ws://{host}:6790/ws`（HTTP 为 `6789` 端口，WS 独立为 `6790`，端口由网关启动参数 `--ws-port` / 配置项 `gateway.ws_port` 决定）。
- 服务端握手仅校验 `Upgrade: websocket` 升级请求，**不校验 URL 路径**，统一约定使用 `/ws`。
- 心跳：走标准 WebSocket `Ping`/`Pong` 帧（协议层自动应答），前端使用标准 WS 客户端库即可，无需额外处理。

### 2.2 整体交互流程

WebSocket 对接需严格遵循固定流程，**认证为前置必要步骤**：

1. 建立 WebSocket 长连接；
2. 发送认证消息 `auth_request`，接收服务端 `auth_response`，认证成功后方可执行业务请求；
3. 发送对话请求 `chat_stream`，发起 AI 对话；
4. 持续接收服务端 `event` 系列推送事件，`message_end` 为对话结束唯一有效标记；
5. 接收 WS 专属 `message_ack` 消息，代表本次对话请求完整闭环；
6. 请求过程中可随时发送 `chat_cancel` 终止请求，收到 `cancelled` 事件即代表取消生效。

> 注意：未完成认证的连接，直接发送业务消息会被服务端拦截，返回 `{"type":"error","data":{"message":"Not authenticated"}}`。

### 2.3 客户端发送消息格式

所有客户端 → 服务端消息为 JSON，`type` 必填；`id`、`correlation_id` 可选。支持两种结构：

- **扁平格式（推荐）**：业务字段直接放顶层（与 HTTP 参数统一）；
- **data 包裹格式（兼容旧逻辑）**：业务字段放 `data` 内。

服务端返回的所有消息统一信封为：

```json
{
  "type": "<消息类型>",
  "id": "<uuid>",
  "data": { },
  "timestamp": "2026-08-13T10:00:00",
  "correlation_id": "<请求关联ID>"
}
```

### 2.4 认证消息（auth_request / auth_response）

所有业务请求的前置认证，格式固定：

```json
{
  "type": "auth_request",
  "id": "auth-001",
  "data": {
    "method": "token",
    "token": "任意token",
    "user_id": "admin"
  }
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `type` | 是 | 固定值 `auth_request` |
| `id` | 否 | 自定义消息唯一标识 |
| `data.method` | 是 | 固定值 `token`（当前唯一认证方式） |
| `data.token` | 是 | 认证令牌。测试阶段服务端不校验内容，直接放行并保存 `user_id` |
| `data.user_id` | 否 | 用户身份标识，不传默认取值 `default` |

认证成功响应（`type=auth_response`）：

```json
{
  "type": "auth_response",
  "data": { "success": true, "method": "token" }
}
```

认证失败响应：`{"success": false, "error": "<原因>"}`（如未知认证方式、认证失败）。

### 2.5 发起流式对话（chat_stream）

支持两种请求格式，**优先使用扁平格式**，可与 HTTP 接口参数统一，降低开发维护成本。

✅ 扁平格式（推荐）：

```json
{
  "type": "chat_stream",
  "message": "用户输入的内容",
  "session_id": "会话ID",
  "user_id": "admin",
  "agent_id": "kunming",
  "correlation_id": "req-trip-001"
}
```

🟡 data 包裹格式（兼容旧逻辑，不推荐）：

```json
{
  "type": "chat_stream",
  "id": "stream-001",
  "correlation_id": "req-trip-001",
  "data": {
    "message": "用户输入的内容",
    "session_id": "会话ID",
    "user_id": "admin",
    "agent_id": "kunming"
  }
}
```

字段说明与 HTTP 请求参数完全一致，见 **第 4 节**。补充 WS 特有规则：

- `message` 为 JSON 对象时（如告警研判），后端会自动 `json.dumps` 序列化，前端直接传对象即可；
- `correlation_id`：**建议显式传入**。它是链路追踪与 `chat_cancel` 精准取消的唯一依据；若不传，服务端内部会生成 UUID 用于取消注册，但**响应消息中该字段为 `null`**，无法按 ID 关联与取消。

### 2.6 取消请求（chat_cancel）

用于终止正在执行的流式对话请求，**仅 WebSocket 支持**：

```json
{
  "type": "chat_cancel",
  "data": {
    "correlation_id": "req-trip-001"
  }
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `type` | 是 | 固定值 `chat_cancel` |
| `data.correlation_id` | 是 | **必须与待终止 `chat_stream` 请求的 `correlation_id` 完全一致** |

取消生效后，服务端会先推送一个 `cancelled` 事件（`data.data.message="对话已中止"`），随后返回 `message_ack`；若流已结束或 ID 不存在，仍返回 `message_ack`（`success: true`）。

### 2.7 服务端推送事件（event 信封格式）

`chat_stream` 过程中，服务端逐条推送 `type=event` 的消息，信封格式与 HTTP-SSE 事件**完全一致**：

```json
{
  "type": "event",
  "id": "uuid",
  "data": {
    "event_type": "实际事件类型",
    "data": {},
    "session_id": "会话ID",
    "correlation_id": "req-trip-001"
  },
  "timestamp": "2026-08-13T10:00:00",
  "correlation_id": "req-trip-001"
}
```

前端核心解析关注点：

1. `data.event_type`：事件业务类型，用于前端分支渲染、逻辑处理；
2. `data.data`：当前事件携带的核心业务数据；
3. `correlation_id`：请求级唯一标识，同一次对话的所有事件该值一致；
4. `session_id`：会话级唯一标识，同一个会话全程固定不变。

全部 `event_type` 清单与业务字段见 **第 7 节**。其中 `message_end` 是**对话结束唯一有效标记**。

### 2.8 专属消息：message_ack（仅 WebSocket）

在 `message_end` 事件推送完成后发送，代表本次对话请求完全闭环、执行完毕。**SSE 接口无此消息。**

`chat_stream` 结束后返回的 `message_ack`：

```json
{
  "type": "message_ack",
  "data": {
    "received": true,
    "type": "chat_stream",
    "success": true,
    "message": "完整响应内容",
    "session_id": "stream-001",
    "user_id": "admin",
    "session_summary": "会话摘要",
    "execution_flow": [],
    "audit_log_id": "",
    "gateway_elapsed_ms": 0,
    "is_new_session": true,
    "stream_complete": true,
    "manager_summary": ""
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `success` | 本次对话是否成功 |
| `message` | 完整响应内容（`full_response`） |
| `session_id` | 实际使用的会话 ID |
| `session_summary` | 会话摘要 |
| `is_new_session` | 是否新建会话 |
| `stream_complete` | 恒为 `true`，标识流式闭环完成 |
| `execution_flow` | 实际执行流程（按需展示） |
| `audit_log_id` / `gateway_elapsed_ms` | 审计日志 ID、网关耗时（毫秒） |
| `manager_summary` | 管理器摘要（可能为空） |

### 2.9 非流式对话（chat）

`chat` 消息结构与 `chat_stream` 完全一致（仅 `type` 不同），服务端收集完整事件后**只回一条 `message_ack`**，`data.events` 携带完整事件时间线：

```json
{
  "type": "chat",
  "message": "用户输入的内容",
  "session_id": "会话ID",
  "user_id": "admin",
  "agent_id": "kunming"
}
```

`message_ack.data` 中：`type:"chat"`、`message` 为最终回复、`events` 为完整事件数组（结构与流式逐事件一致，可复用解析逻辑）。不支持取消。

### 2.10 会话管理（WS 方式）

WS 同样支持会话管理消息：`list_sessions`、`get_session`、`create_session`、`delete_session`、`get_session_messages`，统一回 `message_ack` / `error`。参数与 HTTP 会话接口一致，详见《前端对接文档_会话历史.md》。

### 2.11 WebSocket 最简对接流程

1. 建立 WebSocket 长连接（`ws://{host}:6790/ws`）；
2. 发送 `auth_request` 完成认证，确认 `auth_response.success === true`；
3. 发送 `chat_stream` 请求发起对话（携带 `correlation_id`）；
4. 循环监听、解析 `event` 事件，直至收到 `message_end`；
5. 接收 `message_ack`，确认本次请求完全闭环。

### 2.12 完整 WebSocket 消息类型总览

除对话相关外，WS 还承载会话、用户、任务等消息。**客户端 → 服务端**类型：

| 消息 type | 说明 |
| --- | --- |
| `ping` | 心跳（协议层通常自动应答 `pong`） |
| `auth_request` | 认证（前置步骤） |
| `message` | 通用消息 |
| `command` | 通用指令 |
| `subscribe` | 订阅某类事件（`data.event_type`，如 `task:xxx`） |
| `unsubscribe` | 取消订阅 |
| `chat` | 非流式对话 |
| `chat_stream` | 流式对话 |
| `chat_cancel` | 中止流式对话（需 `correlation_id` 一致） |
| `list_sessions` | 列出会话 |
| `get_session` | 会话详情 |
| `create_session` | 创建会话 |
| `delete_session` | 删除会话 |
| `get_session_messages` | 会话消息历史 |
| `user_login` / `user_logout` | 用户登录 / 登出 |

**服务端 → 客户端**类型：

| 消息 type | 说明 |
| --- | --- |
| `pong` | 心跳应答 |
| `auth_response` | 认证结果 |
| `message_ack` | 请求闭环确认 |
| `error` | 错误（如未认证 `Not authenticated`） |
| `event` | 对话流式事件（`data.event_type` 分支） |
| `broadcast` | 广播消息 |
| `task_progress` | 任务进度更新 |
| `task_audit` | 任务审计日志（**枚举已定义，推送实现以实际为准**） |
| `task_status` | 任务状态变更 |
| `task_complete` | 任务完成 |

> 任务类推送多用于任务执行实时刷新，前端如需订阅某任务，先发 `subscribe`（`data.event_type="task:<task_id>"` 或 `"task:*"`）。会话/用户/任务对应的 REST 接口分别见《前端对接文档_会话历史.md》《前端对接文档_用户管理.md》《前端对接文档_任务管理.md》。

## 3. 鉴权方式（HTTP）

鉴权契约（身份头 `X-User-Id`、默认安全、403 格式、WebSocket 的 `user_id`）见《前端对接文档_用户管理.md》「2. 权限模型与鉴权契约」。

对话接口的特殊规则：
- 每个 HTTP 对话请求必须带身份头 **`X-User-Id`**；
- `chat` / `chat/stream` 均要求 **`write`** 权限（代码中 `required_level="write"`）：
  - `admin` / `user`：可正常对话；
  - `guest`：被网关在路由层拦截，返回 `HTTP 403`、`{ "success": false, "error": "无权限" }`。

```js
fetch('http://网关/api/v2/chat', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-User-Id': 'admin'
  },
  body: JSON.stringify({ message: '今天保供电跳闸情况', agent_id: 'kunming' })
})
```

## 4. 请求参数（HTTP 与 WS 扁平格式通用）

| 字段 | 必填 | 类型 | 说明 |
| --- | --- | --- | --- |
| `message` | 是 | string / object | 用户输入。普通场景传字符串；`alert_judge` 场景必须传 JSON 对象（后端会自动序列化为字符串） |
| `session_id` | 否 | string | 会话 ID。不传自动新建会话；传入已有 ID 延续上下文做多轮对话 |
| `user_id` | 否 | string | 用户身份，缺省 `default` |
| `agent_id` | 否 | string | 指定智能体。不传由后台管理器自动路由；传 `auto` 表示自动匹配。**指定 `mcp` 时**：缺省默认用智能体 `dfecrab` |
| `correlation_id` | 否 | string | 请求级唯一 ID，用于链路追踪 / 取消（**仅流式接口支持**）。WS 端建议显式传入，不传则服务端响应不回显（见 2.5）；HTTP 侧仅参与追踪 |
| `knowledge_base` | 否 | bool/string | **短路分支**：任意非空值即触发知识库直答，直接调 6788 `/knowledge/chat`（见 6.4） |
| `kb_category` | 否 | string | 配合 `knowledge_base`：知识库文档分类过滤（支持自定义分类） |
| `kb_top_k` | 否 | int | 配合 `knowledge_base`：召回切片数，默认 5 |
| `mcp` | 否 | string / string[] | **短路分支**：MCP **服务名**或**服务名数组**，运行时临时绑定该 agent 的 MCP 服务（见 6.5） |

> ⚠️ **互斥规则**：`knowledge_base` 与 (`agent_id` 或 `mcp`) **互斥**；`agent_id` 和 `mcp` **可以共存**（`agent_id` 决定用哪个 agent，`mcp` 决定临时可用的 MCP 服务）。同时触发互斥时返回错误 `knowledge_base 与 agent_id/mcp 参数互斥`。

> ⚠️ `message` 为 JSON 对象时（如告警），后端 `isinstance(message, dict)` 会自动 `json.dumps` 成字符串，前端无需手动序列化，但也不要序列化后传字符串。

## 5. HTTP 非流式接口 `POST /api/v2/chat`

### 5.1 请求

```json
{
  "message": "今天保供电跳闸情况",
  "session_id": "chatstream_test_001",
  "user_id": "admin",
  "agent_id": "kunming"
}
```

### 5.2 成功响应（HTTP 200）

后端收集完整 `events` 后一次性返回（`grpc_server.py:_handle_chat`）：

```json
{
  "success": true,
  "message": "ReAct 循环执行完成",
  "data": {
    "response": "完整回复内容",
    "session_id": "chatstream_test_001",
    "session_summary": "会话摘要",
    "is_new_session": true,
    "intent": "task",
    "events": [
      { "type": "meta", "data": { "session_id": "...", "is_new_session": true, "agent_id": "kunming" } },
      { "type": "manager_decision", "data": { "intent": "task", "target_agent": "kunming", "parameters": {}, "missing_params": [], "reasoning": "..." } },
      { "type": "tool_call", "data": { "tool_name": "kunming_api", "tool_args": { "...": "..." } } },
      { "type": "tool_result", "data": { "tool_name": "kunming_api", "result": { "...": "..." }, "success": true } },
      { "type": "message_end", "data": { "full_response": "完整回复内容", "tool_calls": [], "tools_used": [], "iterations": 2, "agent_id": "kunming" } }
    ],
    "tool_calls": [
      { "tool_name": "kunming_api", "arguments": { "...": "..." } }
    ],
    "matched_skills": []
  }
}
```

### 5.3 响应字段说明

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `success` | boolean | 是否成功 |
| `message` | string | 固定文案 `ReAct 循环执行完成` |
| `data.response` | string | **最终完整回复**（唯一取回答的地方） |
| `data.session_id` | string | 本次实际使用的会话 ID（新建或复用） |
| `data.session_summary` | string | 会话摘要 |
| `data.is_new_session` | boolean | 是否新建会话 |
| `data.intent` | string | `task` / `chat` / `complex` |
| `data.events` | array | 完整事件时间线（结构与流式逐事件一致，可复用同一套解析） |
| `data.tool_calls` | array | 本次调用的工具摘要（`tool_name` + `arguments`） |
| `data.matched_skills` | array | 匹配到的技能 |

> 注意：HTTP 非流式下 `events` **非空**（后端仍收集并返回完整时间线）。若只需最终答案，直接读 `data.response` 即可；若要渲染执行链路/思考过程，解析 `data.events`。

### 5.4 异常响应

- `message` 为空 → `HTTP 400`，`{ "success": false, "error": "message is required", "details": {...}, "build_hint": "请提供非空的 message 参数" }`
- 内部异常 → `HTTP 5xx`，`{ "success": false, "error": "<异常信息>" }`

## 6. HTTP SSE 流式接口 `POST /api/v2/chat/stream`

### 6.1 请求

与 5.1 完全一致，额外可选 `correlation_id`：

```json
{
  "message": "今天保供电跳闸情况",
  "session_id": "chatstream_test_001",
  "user_id": "admin",
  "agent_id": "kunming",
  "correlation_id": "req-trip-001"
}
```

### 6.2 响应

- 响应头：`Content-Type: text/event-stream`
- 每行固定格式：`data: {json字符串}\n\n`

**核心解析规则：**
1. 截取 `data: ` 之后的 JSON，事件结构与 WebSocket `event` 完全一致，可复用同一套解析逻辑。
2. **收到 `message_end` 即代表对话结束**，此时应停止读取、关闭连接。
3. SSE 不支持手动取消（无 `cancelled` 事件、无 `message_ack`）。

### 6.3 事件信封格式

```json
data: {"type":"event","id":"uuid","data":{"event_type":"message_end","data":{...},"session_id":"...","correlation_id":"req-trip-001"},"timestamp":"2026-08-21T14:33:26","correlation_id":"req-trip-001"}
```

前端解析关注点（同 WS）：
- `data.event_type`：事件业务类型，用于分支渲染
- `data.data`：事件核心业务数据
- `correlation_id`：请求级唯一 ID，同一次对话所有事件一致
- `session_id`：会话级唯一 ID

### 6.4 知识库直答分支（`knowledge_base`）

请求体带 `knowledge_base`（任意非空值，建议 `true`）即触发，网关直接调知识库服务，跳过 Manager / ReAct，**响应更快**：

```json
{
  "message": "调度操作基本要求",
  "session_id": "kb_test_001",
  "user_id": "admin",
  "knowledge_base": true,
  "kb_category": "power_grid",
  "kb_top_k": 3
}
```

**事件流**（以流式为例）：
1. `meta`
2. `manager_decision`（`intent=knowledge_base`，`target_agent=knowledge_base`）
3. `message_start`
4. 多个 `message`（答案按 80 字符分块）
5. `message_end`（`full_response` = 完整答案，`sources` = 引用来源，`matched_skills=["knowledge_base"]`）

非流式接口收集事件后 `data.response` = 完整答案。知识库服务不可用时，`message_end.full_response` 为错误文案。

### 6.5 MCP 直调分支（`mcp`）

请求体带 `mcp`（**MCP 服务名**或**服务名数组**）即触发。网关跳过 Manager / ReAct，走**指定 agent 的正常 ReAct 流程**，只是把该 agent 可用的 MCP 服务**临时限定**为 `mcp` 里列出的服务；LLM 在限定服务内自动决定调哪个工具、传什么参数。

**执行上下文**：`agent_id or "dfecrab"` —— 传了 `agent_id` 就用该 agent（其 system_prompt / 本地技能 / 迭代上限生效）；只传 `mcp` 则默认用智能体 `dfecrab`。

**服务名是 `config/mcporter.json` 里配置的 MCP 服务名**（如 `kdocs`、`weather`），且该服务需 `enabled`。对话里传的 `mcp` 只是**运行时临时绑定**，不修改 `mcporter.json` 里的 `bound_agents`。

**单服务示例**：
```json
{
  "message": "北京今天天气怎么样",
  "session_id": "mcp_test_001",
  "user_id": "admin",
  "mcp": ["weather"]
}
```

**多服务 + 指定 agent 示例**：
```json
{
  "message": "查一下 kdocs 里的调度规程",
  "session_id": "mcp_multi_001",
  "user_id": "admin",
  "agent_id": "kunming",
  "mcp": ["kdocs", "weather"]
}
```

**事件流**（流式，与普通 agent ReAct 一致）：
1. `meta`
2. `manager_decision`（`intent=task`，`target_agent=<agent_id 或 dfecrab>`）
3. `skill_match`（匹配到的技能）
4. `think_start` / `think`（LLM 思考）
5. `tool_call` / `tool_result`（LLM 自动调用限定服务内的 MCP 工具）
6. `message_end`（`full_response` = LLM 归纳的最终回答，`tools_used` = 实际调用的工具）

**校验规则**：
- `mcp` 必须是服务名字符串或服务名数组；过滤后为空则报错 `mcp 参数必须是非空的 MCP 服务名字符串或字符串数组`
- `agent_id` 必须为单个字符串，传数组报错 `agent_id 必须是单个字符串`
- `knowledge_base` 与 (`agent_id` 或 `mcp`) 互斥；`agent_id` 和 `mcp` 可共存
- 指定服务不存在或未启用时，该 agent 将无可用 MCP 工具（LLM 可能走纯文本回答或报无工具）

## 9. 核心约定与注意事项

1. **对话终止判定**：仅 `message_end` 是对话结束唯一标记（非流式下读 `data.response`）。禁止用连接关闭/超时判断完成。
2. **回答来源**：流式读 `message_end.data.full_response`；非流式读 `data.response`；WS 的 `message_ack.message` 兜底。
3. **鉴权**：HTTP 请求必须带 `X-User-Id`；`guest` 无法对话（403）。WebSocket 必须先发 `auth_request` 完成认证，否则业务消息被拦截（`Not authenticated`）。
4. **取消（仅 WS）**：`chat_cancel` 的 `correlation_id` 必须与发起 `chat_stream` 时完全一致，建议发起时显式携带。
5. **解析复用**：WebSocket 与 SSE 事件信封结构完全一致，建议封装通用解析方法。
6. **JSON 入参**：`alert_judge` 的 `message` 传对象，后端自动转字符串，不要手动序列化后传字符串。

## 10. 自测 / 联调命令

```bash
GW=http://网关/api/v2/chat

# 1) 非流式（期望 success:true 且 data.response 有内容）
curl -X POST $GW -H "Content-Type: application/json" -H "X-User-Id: admin" \
  -d '{"message":"你好","agent_id":"default"}'

# 2) SSE 流式（收到 message_end 后结束）
curl -N -X POST http://网关/api/v2/chat/stream \
  -H "Content-Type: application/json" -H "X-User-Id: admin" \
  -d '{"message":"写个 python 打印 hello world 并运行","agent_id":"code_writer"}'

# 3) guest 调用（期望 HTTP 403 无权限）
curl -X POST $GW -H "Content-Type: application/json" -H "X-User-Id: guest" \
  -d '{"message":"hi"}'

# 4) 缺 message（期望 HTTP 400 message is required）
curl -X POST $GW -H "Content-Type: application/json" -H "X-User-Id: admin" -d '{}'
```

WebSocket 联调可用 `wscat` 等标准 WS 客户端，按第 2 节流程操作：连接 `ws://{host}:6790/ws` → `auth_request` → `chat_stream` → 逐条读 `event`，直到 `message_end` + `message_ack`。

## 11. 与历史消息的关系

- 每次对话后，`user` 与 `assistant` 消息会自动落库。
- 回看历史请调 `GET /api/v2/sessions/{session_id}/messages`（详见《前端对接文档_会话历史.md》）。
- 历史消息里 `tool_calls` 为轻量摘要（无 `result`），工具完整结果在 `execution_flow` 中；实时流式事件里 `tool_result` 仍带完整 `result`。
